# Web portal (`3-mikro-webportal`)

A small Flask app with two jobs:

1. **Self-service for people on the network**: from any site, a user opens the portal and toggles
   for *their own IP*:
   - the **DNS filter** (ad/malware blocking, e.g. Pi-hole) off for 24 h or 30 days, or back on,
   - **internet through the VPN exit** (another core, see
     [internet transit](../network-design.md#internet-transit-and-policy-routing)) on or off.
2. **Router boot hook**: `/router_boot_update` lets a router that just booted ask for its
   configuration to be pushed again (see [self-healing](../operations.md#self-healing-boot-hook-and-watchdog)).


## How it works

The portal never touches the DNS server or the routes directly. It edits **firewall address
lists** on the client's own site router, through the REST API, and the firewall rules generated by
the automation act on those lists:

| Action | Address list entry on the client's site router | Effect (rules) |
|--------|-----------------------------------------------|----------------|
| Disable DNS filter 24 h / 30 d | add `ACL4_PORTAL_DNS` (timeout `1d` / `30d`) | `10-fw4_webapp.yml`: DNS from these hosts is NATed to an unfiltered resolver |
| Enable DNS filter | remove that entry | back to the normal resolver |
| Enable VPN | add `ACL4_PORTAL_VPN` | `internet` configlet: traffic marked into the `internet_vpn` table |
| Disable VPN | remove that entry | normal internet |

Entries are commented `auto_webapp_ACL4_PORTAL_<DNS|VPN>_<ip>`. Keep `auto_webapp_` in
`LOCALSTRING`, otherwise every push deletes them.

The client's site is found from its source IP: the inventory device whose `subnetv4` contains it
(only `10.0.0.0/8` clients are served).

### Routes

| Route | Description |
|-------|-------------|
| `GET /` | Status page for the caller's IP. |
| `GET /enable_pihole`, `/disable_pihole`, `/disable_pihole_forever` | DNS filter on / off 24 h / off 30 d. |
| `GET /enable_vpn`, `/disable_vpn` | VPN exit on / off. |
| `GET /router_boot_update` | If the caller is a router (`mgmt_int` of a device, inside `mgmt_allow_subnet` of `control.yml`), runs `python3 $MAIN_AUTO_PY_EXEC <device>` in the background and answers `ok`; otherwise `device_not_found`. |

When testing from the portal host itself (`127.0.0.1`), the IP is mapped to a lab client
(`10.22.1.2`) and a lab router (`192.168.88.11`).

## Setup

`.env` (see [environment](../configuration/environment.md#web-portal-3-mikro-webportal)):

```bash
CONFIG="config"
CONTROLPATH="control"
MIKRO_USER="automation"            # needs write access to the address lists (REST API)
MIKRO_PASSWORD="..."
MAIN_AUTO_PY_EXEC="1-mikro-auto/mikro_main.py"
ORG_NAME="My Network"
PORTAL_HOME_URL="https://intranet.example.int"   # optional
```

Development server (port 8080, from the repository root):

```bash
DEBUGMODE=1 .venv/bin/python 3-mikro-webportal/app.py
```

Production: serve the WSGI object `application` with a WSGI server, from the portal folder so the
templates resolve, e.g.:

```bash
cd 3-mikro-webportal && ../.venv/bin/pip install gunicorn && \
  ../.venv/bin/gunicorn -w 2 -b 0.0.0.0:8080 app:application
```

Paths in `.env` are relative to the working directory: use absolute paths when running from the
portal folder. For the boot hook, set `BOOT_UPDATE_URL=http://<portal>/router_boot_update` for the
automation, and allow the routers to reach the portal.

## Caveats

- **No authentication.** Anyone who can reach the portal can toggle the filter/VPN for their own
  IP, and any address in `mgmt_allow_subnet` that matches a router's `mgmt_int` can trigger a push
  of that router. Expose it only on internal networks. See [Security](../security.md).
- The inventory is loaded once at start-up: restart the portal after inventory changes.
- TLS certificates of the routers are not verified.
